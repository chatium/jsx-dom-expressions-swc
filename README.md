# jsx-dom-expressions (SWC)

A Rust/SWC port of [`babel-plugin-jsx-dom-expressions`](https://github.com/ryansolid/dom-expressions),
so a Rust toolchain can compile Solid JSX in-process instead of shelling out to Node and Babel.

```rust
let errors = Errors::default();
program = program
    .apply(resolver(unresolved, top_level, false))
    .apply(jsx_dom_expressions(
        Config { module_name: "solid-js/web".into(), ..Default::default() },
        &comments,
        errors.clone(),
    ));
assert!(errors.is_empty());
```

## Which upstream version

The port targets upstream **0.36.10**, and `tools/` pins that version of the plugin to
generate the goldens from.

## What is ported

Both generators the Solid toolchain uses, at every option the upstream test suite covers:

| Config | Upstream suite | Status |
| --- | --- | --- |
| `generate: "dom"` | `__dom_fixtures__` | ✅ |
| `generate: "dom"`, `hydratable` | `__dom_hydratable_fixtures__` | ✅ |
| `generate: "dom"`, no effect/memo wrapper | `__dom_wrapperless_fixtures__` | ✅ |
| `generate: "ssr"` | `__ssr_fixtures__` | ✅ |
| `generate: "ssr"`, `hydratable` | `__ssr_hydratable_fixtures__` | ✅ |

Not ported: the `universal` generator and `generate: "dynamic"`, neither of which Solid's
DOM/SSR builds use. `universal` targets a non-DOM runtime — it emits `createElement` /
`insertNode` / `setProp` calls instead of an HTML template, which is how `solid-three` and the
native renderers work. `dynamic` is not a generator but a router: given
`renderers: [{ name: "dom", elements: [...] }]` it picks per tag, so `<div>` compiles to a DOM
template while `<mesh>` in the same tree compiles to `createElement`, importing both runtimes
into one file.

Where the Babel plugin throws — invalid HTML nesting, a fragment nested inside an element —
this pass records a `CompileError` on the `Errors` handle and carries on, so malformed user
input cannot take a compiler process down. Check `errors` before using the output.

## How it is tested

`tests/cases/` holds the upstream fixtures, each suite as the original whole file plus one
file per top-level statement for granular diffs, alongside a hand-written `usage` suite of
sources shaped like real application code (checked under all four configurations). `tests/expected/` is generated by running
the **real Babel plugin** over them (`node tools/gen.mjs`, options in `tools/configs.json`,
which the Rust tests read too, so the two sides cannot drift).

Both sides are printed by SWC, so only the AST has to match, never Babel's formatting.
`*_through_the_consumer_pipeline` repeats the comparison with `hygiene` and `fixer` applied
to both sides — the treatment a host gives the Babel plugin's printed output — which is what
makes this a drop-in replacement rather than merely an equivalent one.

Note that the goldens are **not** upstream's committed `output.js` snapshots. Those were
taken with an older `@babel/traverse` and no longer reproduce: in 20 of 45 fixture groups they
differ from what the same plugin emits today, entirely in the uid suffix sequence
(`_el$10` where current Babel produces `_el$0`). Matching them would mean reproducing behavior
that no longer exists in production. `tools/verify-goldens.mjs` re-derives every golden with a
given checkout of Babel and the plugin, which is the check that actually matters:

```bash
node tools/verify-goldens.mjs <dir with node_modules holding @babel/core + the plugin>
```

`src/constants.rs` and `src/nesting.rs` are generated from the upstream sources by
`tools/gen-constants.mjs`; do not hand-edit them.

```bash
cargo test
cargo fmt --check && cargo clippy --all-targets -- -D warnings

# refresh fixtures/goldens against a dom-expressions checkout at the pinned commit
(cd tools && npm ci)
node tools/split.mjs <dom-expressions>     # 1d04cc14 == v0.36.10
node tools/gen.mjs
node tools/gen-constants.mjs <dom-expressions>
```

Escaping dominates the SSR halves because that generator puts most of the page into string

Where Babel rejects a source, this pass reports the same diagnostic: the three files in the
corpus that Babel refuses (`<tr>` under `<table>`, `<div>` under `<tbody>`, `<ul>` under `<p>`)
produce exactly those messages here.

```bash
cargo run --release --example corpus-compare -- lower <project> <out> [source filter]
CORPUS_MODULE=solid-js/web cargo run --release --example corpus-compare -- check <out>
```

The two non-identical buckets are consequences of the path being replaced, not of the
transform. Today the Node helper prints to text and SWC re-parses it, so Babel's formatting is
baked in: multi-line comments carry Babel's indentation, and non-ASCII strings arrive already
escaped as `\uXXXX`. Compiling in-process keeps the source's own spelling instead. Same AST,
same behavior, different bytes — so expect those files' goldens to move once on the switch.
Emitting with codegen's `ascii_only` would close the string half of the gap if that matters.

Seventeen real bugs were found this way and are pinned in
`tests/cases/usage/app/07-regressions.jsx`; see that file for what each one was. Every one
of them was a place where SWC's AST or Babel's traversal order differs subtly from what the
plugin's code reads as — none were visible in the upstream fixture corpus.

## Performance

`examples/bench.rs` times the pass over a directory of lowered sources, reporting parse and
transform separately so a change that does nothing cannot look like a win:

```bash
cargo run --release --example bench -- <dir of .jsx files> [iterations]
BENCH_TRANSFORM_ONLY=1 cargo run --release --example bench -- <dir> 400   # for profiling
```

Two things moved the number, measured on 874 files (6.1 MiB) from Cap:

| | transform | |
| --- | --- | --- |
| system allocator | 0.235s | |
| `swc_malloc` | 0.144s | **1.6x** |
| `swc_malloc` + the passes below | 0.140s | 1.7x total |

**Link `swc_malloc` in the host binary.** A global allocator can only be set by the final
binary, so this crate cannot do it for you, and it is the single largest factor — larger than
every code change here put together. This AST allocates heavily and mimalloc handles that
pattern far better than the system allocator.

The code changes were worth about 15%, and came from profiling rather than guessing: the pass
used to walk the whole program five times before transforming anything (uid names, bindings,
assignments, reference counts, nesting validation). They are now one walk. The hot maps are
keyed by interned atoms, where SipHash's collision resistance buys nothing, so they use
`rustc-hash`.

Two earlier attempts — borrowing instead of copying in `detect_expressions`, and returning
`Cow` from the string escapers — measured as no change at all. They are kept because the code
is no worse, but they are not why it got faster; the profile said allocation and repeated
traversal, not string handling.

## Using it from a host compiler

Run the JSX transform right after TypeScript stripping and before `hygiene`/`fixer`, and the
Node round trip disappears. Two things to know when wiring it up:

- **Run `resolver` first.** Binding-sensitive branches (component refs, resolvable event
  handlers, `evaluate()` folding through a `const`) look bindings up by `Id`.
- **Pass the emitter's own comment store.** The `/*#__PURE__*/` annotations on template calls
  are comments; a different store drops them and defeats tree shaking.

Two differences survive by construction when you stop round-tripping through Babel's printed
output: multi-line comments keep the source's indentation rather than Babel's, and non-ASCII
string literals keep their characters where Babel escaped them as `\uXXXX`. Same AST, same
behavior, different bytes — so byte-exact goldens downstream move once on the switch.
